# react-practice

Rails API（`board_app`・非公開）に React + TypeScript の
フロントエンドをつないだ練習用リポジトリ。タスクの一覧・追加・完了切替・削除ができる。

**学習の記録を目的にしている。** 作り終えた成果物ではなく、
**何を間違えて、どう確かめて直したか**を残すために公開している。

実務想定のポートフォリオは別にある（`meal-requests`・現在は非公開。応募時に個別に公開）。

## 構成

```
localhost:5173 (Vite + React)
      │  /api/* を proxy
      ▼
localhost:3000 (Rails / board_app)
```

| | |
|---|---|
| React | 19 |
| TypeScript | 7 |
| ビルド | Vite 8 |
| サーバーの状態 | TanStack Query 5（`useQuery` / `useMutation`） |
| 画面の状態 | `useState`（入力中の文字・エラー表示など） |
| API | `fetch` + 型付きヘルパー（`src/api.ts`） |

`/api/tasks` には `authenticate_user!` が付いているため。

## 分かったことの記録

### 1. 古い state を抱え込んだまま送ってしまう（stale closure）

```ts
setTasks(tasks.map(...))        // ✗ この描画時点の tasks を抱え込む
setTasks((prev) => prev.map(...)) // ○ 最新を受け取る
```

**2件を素早く操作すると、後から返ってきた応答が先の結果を上書きする。**
React も TypeScript も何も言わない。

`prev` で直るのは**画面の書き換えだけ**で、**送る値は直らない。**

```ts
body: JSON.stringify({ task: { done: !task.done } })
//                                  ^^^^^^^^^^^ 押した瞬間に、古い配列から決まる
```

同じタスクを素早く2回押すと `{ done: true }` が2回飛ぶ。
サーバーもライブラリも無しで再現できる形にしてある（`closure-practice.js`・学習ログ側に保管）。

**これは 4 で解決した**（送信中そのタスクを押せなくする）。
ただし**直したのは症状のほうで、原因は「送る値を押した瞬間に決めている」こと**。
根本的に消すなら API をトグル（`PATCH /tasks/:id/toggle`）にする。

### 2. カスタムHook に切り出せるものと、切り出せないもの

`useEffect` が3つ同じ形に見えたので、1つの `useFetch` にまとめようとした。
**まとめられたのは1つだけだった。**

| エンドポイント | 取ってきた後 | |
|---|---|---|
| `/api/csrf_token` | 読むだけ | ✅ |
| `/api/tasks` | `addTask` / `toggleTask` / `deleteTask` が**書き換える** | ❌ |
| `/api/boards` | 一覧は読むだけ。`setBoardId` のおまけがある | △ |

理由は [`useFetch`](src/useFetch.ts) の最後の1行にある。

```ts
return { data, loading, error };  // setData は返していない
```

実際に `/api/tasks` を差し替えて `tsc` を走らせると**エラーが10個**出る。
ただし**原因は2つ**（`setTasks` が無い／`tasks` が `null` かもしれない）で、
残り6個は巻き添え。

> **カスタムHook に切り出せるのは「取ってきて、表示するだけ」のもの。**

この先（キャッシュ・再取得・画面間の共有）を自前でやると雪だるま式に増える。
それを引き受ける既製品が TanStack Query で、**使う前に、なぜ要るのかを手で確かめた。**

`useFetch` は 4 で TanStack Query に置き換わり、**いまはどこからも使われていない。**
消していないのは、この節がこのコードを指しているため（学習の記録として残す）。

### 3. `tsc` 緑・`lint` 緑・テスト0本

差し替えの前後どちらも `tsc` と `lint` は緑だった。**その緑のまま、バグは在った。**

CSRFトークンは届くまで `""` なので、その間に「追加」を押すと `POST` が **422** で落ちる。
そして `catch` がこうだった。

```ts
.catch((err) => console.error(err));
```

**画面には何も出ない。** 入力欄に文字が残り、一覧は増えず、エラーも無い。
利用者からは「ボタンが効かない」としか見えない。
`console.error` は DevTools を開いている人にしか見えない。

#### 確かめ方

いきなり画面を触らず、**基準（対照実験）を先に取った。**

```
空トークンで直接 POST      -> 422
正しいトークンで直接 POST  -> 201
```

そのうえで Rails 側の `/api/csrf_token` に `sleep` を仕込んで再現した。
**1回目は再現しなかった**（ブラウザ操作を別々の呼び出しに分けていて、
押すまでに `sleep` より長い時間が経っていた）。
基準があったので「出ないのはおかしい」と判断でき、やり方のほうを直せた。

> **再現しないときは、まず実験のやり方を疑う。そのために基準を先に取る。**

#### 直し方を2段階に分けた

| | 役割 |
|---|---|
| 失敗を画面に出す | 防げなかった失敗を**見せる** |
| 届くまで押せなくする | 防げる失敗を**防ぐ** |

`disabled` の条件には `useFetch` の `loading` を**使っていない。**

| | 取得成功 | 取得失敗 |
|---|---|---|
| `loading` | false | **false** |
| `token` | 入る | **`""` のまま** |

`loading` で判定すると、失敗したときに押せてしまい 422 に戻る。
`disabled={!csrfToken}` にした。

> **「終わったか」と「使えるか」は別の質問。**

### 4. ライブラリを使う前に、無いと何が起きるかを見た

`useFetch` に `setData` を返させれば 2 の問題は消える。その先に何があるかを先に書き出した。

| 起きること | 自分でやること |
|---|---|
| 追加・削除が成功した | 手で配列を組み立て直す |
| 同じタスクを2回押した | **壊れる**（1 の話） |
| タブを2つ開いている | 片方の変更がもう片方に反映されない |
| 通信が失敗した | いま足した1件を**手で巻き戻す** |

これを引き受けるのが TanStack Query。**入れる前に、無いとどうなるかを手で確かめた。**

#### 書き込み後の更新を `invalidateQueries` に任せる

```ts
queryClient.invalidateQueries({ queryKey: ["tasks"] })
```

**「`tasks` というデータ、もう古いよ」と宣言するだけ。** 取り直しは任せる。
自分で配列を組み立てないので、**応答の順番が入れ替わっても壊れない**（1 の事故が構造的に起きなくなる）。

検討して却下した案が2つある。

| | 問題 |
|---|---|
| `setQueryData`（取り直さず直接書く） | 速いが、自分で配列を組む＝1 の事故が戻る |
| `location.reload()` | 下記 |

`location.reload()` は動く。ただしタスク1件追加するたびに **JS バンドル（この時点で 222 kB）を全部やり直し**、
入力欄の文字・選んでいたボード・エラー表示・スクロール位置が消え、
欲しいのは `tasks` だけなのに `/api/csrf_token` と `/api/boards` も巻き添えで取り直す。

そして根本的に、**これをやるなら React である必要が無い**（Rails が HTML を返すのと同じになる）。

> **SPA にする理由は「画面全体を作り直さないこと」。reload はそれを捨てる。**

#### 測って分かったこと：重複排除

同じ画面の読み込みで、こうなった。

```
GET /api/tasks        1回   ← useQuery
GET /api/csrf_token   2回   ← 自前の useEffect（useFetch）
GET /api/boards       2回   ← 自前の useEffect
```

`StrictMode` は開発中わざと effect を2回実行する。
`useQuery` は `queryKey` が住所になっているので**同じ取得だと分かり、1回にまとめる。**

#### `isPending` が連打を止めた

`Api::TasksController#update` に `sleep 3` を仕込み、同じタスクを素早く3回押した。

| | PATCH の件数 |
|---|---|
| 送信中は押せなくする | **1件** |
| 外す（対照） | **3件** |

3件とも同じ値を送っていた。`tasks` は取り直すまで変わらないので、
**3回押しても1回ぶんの効果しかない。**

`isPending` は `useMutation` が持っているので、自前の `useState(false)` は要らない。

#### `catch` の書き忘れを構造的に潰した

3 で `addTask` の `catch` を直したとき、**`toggleTask` と `deleteTask` の2か所を残していた。**
だから次に出た 404 もまた画面に出なかった。

`useMutation` にすると失敗の置き場所が `onError` に決まるので、「ここに書き忘れた」が起きない。

> **1か所直したら、同じ形を全部探す。**

#### 代償

```
222.22 kB → 258.35 kB   （gzip 69.73 → 80.06 kB）
```

**+36 kB（gzip +10 kB）。タダではない。**

### 5. 押すと失敗するボタンを出さない

動作確認で他人のタスクのチェックボックスを押したら、こうなった。

```
PATCH /api/tasks/5   → 404 Not Found    ← 他人のタスク
PATCH /api/tasks/14  → 200 OK           ← 自分のタスク
```

最初「API が、見せているものと触らせるものを一致させていない」と考えた。**これは間違いだった。**

```ruby
before_action :set_task,    only: [ :show ]                      # Task.find
before_action :set_my_task, only: [ :edit, :update, :destroy ]   # current_user.tasks.find
```

**「全員が見られる。編集できるのは所有者だけ」が意図された設計で、404 は正しい動作。**
間違っていたのは画面のほうだった。

ただし React 側は誰のタスクか知りようがなかった。JSON に `user_id` が無いため。
サーバー側に `editable`（真偽値）を足した。

| 渡し方 | 問題 |
|---|---|
| `user_id` をそのまま返す | **誰のものかが全部漏れる** |
| `editable`（真偽値） | 漏れない。行に載っている値の比較なので追加のクエリも出ない |

> **「クライアントが判断できない」は、たいてい API の設計の話。**

`src/TaskItem.tsx` では、押せない理由を2つに分けて持っている。

```ts
const disabled = !task.editable || busy
//               ^^^^^^^^^^^^^^    ^^^^
//               ずっと押せない    終われば押せる
```

確認: 他人のタスクを押しても **PATCH も DELETE も1件も飛ばない。**

### 6. `staleTime` は「誰が変えるか」で決める

`staleTime` は**何秒キャッシュを信じるか**のつまみ。既定値を確かめずに使っていたので測った。

ブラウザのタブを離れて戻ったときの挙動を見たいが、**このやり方は一度失敗した。**

```
blur: 0   focus: 0   visibility: []   hasFocus: false
```

開発に使っているブラウザ枠のページは**最初からフォーカスを持っていなかった。**
「離れて戻る」が一度も起きていないので、取り直されなくて当然だった。

> **測る前に、測定器が動いているかを見る。**

`window` に `visibilitychange` を送る形に変えて計測した（本物のタブ切り替えではなく、
合図だけを送るシミュレーション）。なお `document` に送っても効かない。
ライブラリのソースが `window.addEventListener("visibilitychange", ...)` だった。

| `staleTime` | 操作 | `/api/tasks` の取得 |
|---|---|---|
| 既定（0） | 合図 ×4 | **4件** |
| 30秒 | 30秒以内に ×4 | **0件** |
| 30秒 | 約35秒後に ×1 | **1件** |

ソース側でも確認。`isStaleByTime(staleTime = 0)` ――**既定は 0 ミリ秒**、
取った瞬間から「古い」扱いになる。

#### 値を3つに分けた

書き込み後は `invalidateQueries` が必ず取り直すので、
**`staleTime` が効くのは「戻ってきたとき」だけ。** だから基準は「誰が変えるか」。

| | 誰が変えるか | `staleTime` |
|---|---|---|
| `/api/tasks` | 自分も、他人も | **0**（既定のまま） |
| `/api/boards` | めったに変わらない | **5分** |
| `/api/csrf_token` | セッション中ずっと同じ | **`Infinity`** |

合図を3回送った結果。

```
tasks 1->2->3->4     boards 1->1->1     csrf 1->1->1
```

副産物として、`StrictMode` の二重実行で `boards` と `csrf` が2回ずつ飛んでいたのが
1回ずつになった（3 の節で測ったやつ）。

#### 「写す」のをやめた

`/api/boards` を 2 で「△」にした理由は、取ってきた結果を別の state に写していたから。

```ts
useEffect(() => { ...; if (data.length > 0) setBoardId(String(data[0].id)); }, [])
```

`useQuery` の `data` は写せない。そこで**写すのをやめて、毎回計算する形**にした。

```ts
const [selectedBoardId, setSelectedBoardId] = useState("");
const boardId = selectedBoardId || String(boards[0]?.id ?? "");
```

**state が1つ減り、2 で「切り出せない」とした理由が消えた。**

> **state に写す前に、計算で出せないかを見る。**
